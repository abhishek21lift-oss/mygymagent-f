| F-P0-6 | Redesign: design system, IA and app-wide sweep | ✅ | Done. The tokens were never the problem — being bypassed was: 3,458 hardcoded palette classes against 286 token usages, and `intelligence/page.tsx` carried 123 hardcoded colours with **zero** `dark:` variants, so the topbar theme toggle produced a broken page. Fixed by (a) a precision-operator token layer with picked neutrals, one accent, status kept separate from accent, and a three-level elevation ramp; (b) re-pointing the eight literal palette scales at generated ramps that invert in dark, making 559 compiled utilities theme-aware at once; (c) a chart palette **computed** with the dataviz validator — the first attempt reused the status hues and failed protanopia separation at ΔE 5.8; (d) compact `PageHero`/`StatCard` primitives, which upgraded all 37 pages using them; (e) IA from 11 top-level destinations to 6 work areas plus a Tools block, nothing deleted or redirected; (f) an app-wide sweep taking radial-gradient washes, decorative gradients, glass fills, backdrop-blur, oversized radii, serif headings and xl shadows all to **0**. Verified at every step against the running app with seeded data, in both themes. |
| F-P0-7 | Per-page layout depth for the remaining routes | ✅ | Done, and the root cause turned out to be a missing primitive rather than per-page sloppiness. The redesign shipped one metric tile and one masthead but **no container**, so all twenty-odd routes kept hand-rolling their own section shell — a hardcoded white border and violet-tinted shadow, both fighting the token layer that makes dark mode work. That one string appeared **91 times across 34 files**. `components/shared/panel.tsx` now supplies `Panel` (the frame + a header that is a *label*, not a competing headline) and `MetricStrip` (a figure row that takes no heading, because four labelled tiles do not need a line announcing that they are numbers). Swept: 91 legacy shells, 45 doubled `font-semibold text-xl font-semibold` codemod artifacts, **43 decorative icon chips**, 38 oversized `CardTitle`s, and the last hand-rolled metric components on Inventory and Expenses (each carried four decorations on one number — coloured top bar, blurred orb, 56px rotating icon tile, two-tone shadow). **Three judgement calls beyond the sweep:** (1) `StatCard` no longer paints a state rule on a zero — "Expired: 0" and "Refunded: ₹0.00" were colouring good news, and once several tiles are tinted none of them reads as needing attention; (2) tiles that were not measurements are gone (billing's "Payment activity · Live", CRM's "Current stage", which merely restated the filter tab below it); (3) **every page title now matches the nav item that got you there** — clicking "Memberships" and landing on "Membership Lifecycle" cost a beat of re-orientation each visit, and the "X OS" suffixes named an ambition rather than a screen (19 titles realigned, descriptions added where the old title was reaching for one). Verified by rendering: logged in against a live API and screenshotted the routes at 1512×950 across three rounds, fixing what the pictures showed rather than what the diff claimed. 0 lint errors, clean production build, 27 tests green. |
| F-P0-1 | Real member self-service portal | 🚧 | **Slice 1 done (ADR AI-29): members have real logins and can see their own data.** `/portal` is a member shell with Home (membership + recent visits), Training, Nutrition and Visits, on a phone-first layout. Verified by driving a browser as a real member at 430px. Backend `/portal` takes no memberId on any read route and declares no permission — the member is resolved from their own JWT via `Member.userId` and every query is scoped to that id, so "their own data" is a property of the query rather than a grant. That matters because the audit found the **`MEMBER` role carried `attendance.read`/`workouts.read`/`nutrition.read`** — the org-wide reads `GET /attendance` accepts — so issuing it would have let a member list every check-in in the gym. Its permission list is now empty. **Bigger find, fixed here:** nothing in the codebase ever set `User.status = 'ACTIVE'`, and `login()` refuses anything else — so *every staff member and member ever invited* could set a password and still be told their credentials were wrong. 20 e2e suites flipped the status through Prisma, which is why it survived. `resetPassword` now activates an INVITED account (only INVITED — a suspended account stays suspended). `test/member-portal.e2e-spec.ts` (10) + 2 invite-acceptance cases in the reset suite; 412 e2e green. **Slice 2 done (ADR AI-30): members now actually reach it.** Two things were missing and both were the same shape — a capability with no way to invoke it. (a) The login page hard-coded `router.replace("/dashboard")`, so a member signed in successfully and landed in the staff app where every request 403s and nothing points back; `/portal` was reachable only by typing it. `/auth` now answers `memberId` on the user it returns — on login, on MFA completion, on refresh and on `/auth/me`, all four, because a reload must not lose the decision — and one `homeRouteFor()` is read by both the login page and the staff layout so they cannot drift. The staff layout bounces a member to `/portal`, mirroring what the portal already does to a staff account, and neither paints its shell while redirecting. `completeMfaLogin()` returns its session instead of `void` so a member with a second factor routes the same way. (b) **`POST /portal/enable/:memberId` had no caller anywhere in the UI** — route, permission, invitation email and tests all present, and no gym owner could grant a member a login. That is the sixth missing-writer find of this audit. The member page now carries a Member app access card with the three states that call for different words: no login, invitation outstanding, signed up. `GET /members/:id` returns the login as `{id,email,status}` selected field by field — never `user: true`, which would hand the password hash and MFA secret to every reader — and a test asserts the key set exactly. 6 new e2e cases (16 in the portal suite) + 3 unit cases on `homeRouteFor`; 418 e2e and 99 unit green. Verified in a browser: a member signs in at 430px and lands on `/portal`, typing `/dashboard` bounces them back, a staff account still lands on `/dashboard`, and clicking Invite flips the card to Invitation outstanding. **Remaining for F-P0-1:** class/PT self-booking (write), online renewal/payment, notification preferences, and profile edit. The old one-time-token page at `/member-portal` still works and is now superseded — retire it once members are on logins. |
| F-P0-2 | Business OS UI beyond quick-create forms | ⬜ | `src/app/(app)/business-os/page.tsx` (128 lines) covers loyalty/referrals/support/feedback/marketing/accounting/kiosk with single-shot create forms and flat lists only — no support-ticket thread/reply view (backend has `POST support/tickets/:id/messages` + `PATCH support/tickets/:id`, unused by the UI), no campaign audience preview before enroll, no accounting ledger drill-down beyond trial-balance/tax-summary buttons. Build proper detail views once B-P0-1 (backend Prisma migration) lands — don't invest heavily in UI against the raw-SQL contract first. |
| F-P0-4 | Handle the MFA challenge in login, and add the enrolment UI | ✅ | Done. `POST /auth/login` now returns a discriminated `LoginResult`; `auth-context.tsx` establishes **no** session on `mfaRequired: true` (no token, no user, no `/auth/me`) and exposes `completeMfaLogin`. `login/page.tsx` branches into a code step that accepts a TOTP or a recovery code in one field. `/settings/security` covers status/setup/enable/disable, renders `otpauthUri` as a client-side QR (`qrcode`), offers the setup key for manual entry, and shows the 10 recovery codes once with copy/download behind an explicit acknowledgement. The BFF proxy route became a catch-all (`api/auth/[...action]`) because `mfa/verify` is two segments and must set the refresh cookie the same way `/auth/login` does. 4 new `auth-context` tests, each verified to fail when the `mfaRequired` branch is removed. The Security link sits outside the `settings.manage` gate — 2FA is a personal account setting, not an admin one. **B-P0-10 (mandatory MFA for privileged roles) is now unblocked.** |
| F-P0-5 | Handle the organization MFA policy in the client | ✅ | Shipped alongside `mygymagent-b` B-P0-10, because enforcement without it would 403 every page. `mfaEnrolment: { state, deadline }` now rides on the login response and `/auth/me` and is tracked in `auth-context`. On `ENFORCED` the `(app)` layout replaces the whole shell with `MfaRequiredGate` — the shell’s own chrome (nav counts, notification centre, branch picker) fetches data the confined session cannot read, so rendering it would bury the one available action in 403s. On `GRACE`, a non-dismissible `MfaGraceBanner` shows the deadline (dismissible would mean a warning seen on day one and never again on day thirteen). The enrolment flow was extracted to `components/security/mfa-enrolment.tsx` so the gate and the settings screen cannot drift. `/settings/security` gained the admin policy section — enrolment report above the switch — gated on `organizations.update`. 9 new tests; the banner’s state check was broken to confirm they detect it. |
